# Fake sensor API

A standalone FastAPI service that mimics the real, currently-offline
`geosenzor-api` (see `../data/verdantis-sensor-infra-reference.md`) closely
enough that `docs/sensors/simulation.html` can be built and demoed against it
today, then pointed at the real API later with minimal changes.

Not wired into the rest of this repo in any way - `config.py`/`clients.py`
never import this folder, and nothing here writes into `outputs/`. It's a
dev tool you run yourself, same "nothing runs automatically" posture as
everything else in this repo (see the root `CLAUDE.md`).

## What it simulates

- **6 static sensors** (`sensor01`-`sensor06`), spread in a grid across the
  Devinska plot's real `alert_bbox`. Each reports temperature + soil moisture
  on the same cadence/shape as the real `tempsensor` MQTT topic
  (`sensor_id`, `location`, `temperature`, `soil_moisture`, `date_time`).
- **1 moving sensor** (`tractor01`), linearly interpolating back and forth
  between two waypoints inside the same bbox - a tractor/vehicle working the
  plot. Reports position on the same shape as the real `geosensor` topic
  (`latitude`, `longitude`, `altitude`, `satellites`, `hdop`, `fix`).
- A **crop/season critical soil-moisture table** (`config.json`'s
  `crop_seasonal_critical_soil_moisture`) - deterministic, swappable per crop
  and season without touching any code, feeding the dashboard's
  "critically low" status bar.

Every reading's *value* is a deterministic function of (sensor, timestamp) -
see `simulator.py` - so re-running the generator doesn't change the shape of
the data, only how much of it covers.

## Two ways to run this, for two different purposes

**`docs/sensors/simulation.html` (the published page) reads a static
snapshot - it does NOT poll this API.** This site has no backend (see the
root README), so nothing served from `docs/` can poll a live server anyway.
`generate_snapshot.py` runs the same generator this API uses and writes the
result straight into `docs/sensors/data/sim_*.json` as plain static files -
the same "static files, regenerated by hand" pattern every other page here
already uses (compare `publish_site.py`).

```bash
pip install -r sensor_fake_api/requirements.txt
python sensor_fake_api/generate_snapshot.py
```

Re-run it whenever you want the "past 10 days" window to actually cover the
last 10 days, or want a different sensor layout/threshold (edit
`config.json` first) baked into the published page. Nothing commits/publishes
automatically - review and commit `docs/sensors/data/sim_*.json` like any
other change.

**`app.py` (a live local server) exists separately**, for anyone who wants a
genuinely live, polling version to develop against, or to exercise the API
shape directly (curl, a different frontend, etc.) - it is NOT what the
published page talks to.

```bash
cd sensor_fake_api
uvicorn app:app --reload --port 8000
```

10 days of history is backfilled at startup (`backfill_interval_seconds`,
default 15 min/point); after that, one new reading per sensor is appended
every `update_interval_seconds` (default 30s, matching the real sensor's
observed cadence) for as long as the server keeps running.

## Endpoints (the live server, `app.py`)

Mirrors the real API's contract (query params, `{"data": [...]}` envelope,
chronological order, optional `X-API-Key` header - see
`../data/verdantis-sensor-infra-reference.md` section 6):

- `GET /api/v1/temperature` - `sensor_id`, `location`, `from`, `to`, `last`
  (default 200, clamped to 1000), `after_id`
- `GET /api/v1/location-data` - same params, for the moving sensor's position
- `GET /health` - liveness + current row counts

One addition with **no** real-API equivalent, clearly namespaced so it's
never mistaken for part of the contract above:

- `GET /api/v1/sim/config` - bbox, the static sensor registry (id/location/
  lat/lon - the real API never returns coordinates for a tempsensor, only a
  location *label*; a real deployment gets that mapping from
  `clients/<slug>.json`'s `sensor_location` instead, same idea here via
  `config.json`), and the active crop/season's critical soil-moisture value.
  `generate_snapshot.py` writes this same payload (plus `generated_at`) to
  `docs/sensors/data/sim_config.json`.

`require_api_key` in `config.json` defaults to `false` for frictionless local
use; flip it and set `api_key` to exercise the same `401` behavior the real
API has.

## Swapping to the real API later

Both paths point at this same `simulator.py`/`config.json` core, so there are
two independent things to swap, depending which one you're using:

- **The published page**: write a new generator (or extend
  `generate_snapshot.py`) that pulls from `https://api.verdantisdata.eu`
  (with a real `X-API-Key`) instead of `simulator.generate_backfill()`, and
  a real sensor-placement source (e.g. a `clients/<slug>.json`-style file)
  instead of `config.json`'s `static_sensors` - but keep writing the same
  `docs/sensors/data/sim_*.json` shapes, so `simulation.html` itself needs no
  changes.
- **The live server**: point a frontend at `https://api.verdantisdata.eu`
  instead of `http://localhost:8000` - the query params and response shape
  already match, per the "Endpoints" section above.
